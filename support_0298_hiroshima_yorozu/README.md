## 履歴と失敗時の挙動

- 検証初回のXMLは全件入りの照合用。運用時の初回は、目視照合で `publish` とした記事だけRSSに載せ、`history` とした記事も照合用の履歴には保全する。初回に公開対象が0件なら、確認済みの履歴だけを登録し、新規記事を確認した時点で最初のRSSを公開する。
- 2回目以降は新しいWordPress IDを追加し、一覧から外れた記事も保持する。再掲、見出し修正、リンクの変更があっても同じIDを引き継ぐ。既に非公開扱いにした初回履歴も、後から一覧に再掲されただけでは配信対象に戻らない。
- 全一覧・全ページ・記事詳細・サイトマップの照合を同じ実行で完了してから候補を作る。取得失敗、一覧の空化、ページ送りの異常、照合不一致、識別情報の異常、既存履歴とRSSの不一致時は公開処理に進まない。有効な過去記事がある場合に空RSSを書き込む経路は設けていない。
- 本番更新時は履歴とRSSを一緒にコミットする。他のフィードの変更とは共存できる。同時に0298のデータや処理に変更が入った場合は古い結果の反映を止める。
- サイトの投稿形式変更、対象一覧が実際に0件になった場合、サイト移行に伴うWordPress IDの振り直しは再調査が必要。記事の修正は同じGUIDで反映するため、Inoreader側が修正を通知するかは公開後に確認する。蓄積した履歴の削除や切り詰めは、再通知への影響を別途確認する。

## 承認後の反映手順

1. 進行管理で監視範囲と初回の掲載方針を承認する。検証スナップショットの履歴を既存購読 `0298_広島県よろず支援拠点` と照合する。旧公式フィードは取得停止中のため、旧配信分の照合にはInoreaderの既存履歴を使う。URLがサイト移行で変わっている場合は、見出しと記事内容・開催日等を照合する。旧履歴や既読情報をリポジトリに入れない。
2. 成果物の `cutover-review.json` を手元に保存する。全GUIDについて、今回初回から配信することを確認したものを `publish`、旧購読で確認済みまたは今回初回配信を見送ると承認したものを `history` に記入する。未照合の記事が残る場合は進行管理で判断する。
3. 本番承認後、最新 `main` を起点にした作業場所で、下記のコードとテストを取り込む。検証用のWorkflow、旧検証スクリプト、比較用の全件RSS、照合表は取り込み対象外。テスト後、承認済み照合表を使って初回用の候補を新規ディレクトリに生成する。前回検証以降に記事が追加・削除されID集合が変わっていれば処理は止まるため、最新の照合用プレビューを作って差分を確認する。

   ```sh
   python -m pip install beautifulsoup4==4.15.0
   python -m unittest discover -s tests/hiroshima_yorozu -v
   python scrape_support_0298_hiroshima_yorozu.py \
     --source . --output /tmp/hiroshima-0298-approved \
     --bootstrap-review /path/to/cutover-review.json
   ```

4. 生成結果を確認し、コード、テスト、本番Workflow、初回履歴と、初回配信対象がある場合のRSSをまとめて反映する。反映後はWorkflowを最初に `publish: false` で実行し、候補と履歴を照合する。定期実行は07:47 JSTを設定しており、起動時刻はActionsの待ち行列により遅れる場合がある。
5. [配信予定URL](https://es-worktools.github.io/jnet21-rss/support-0298-hiroshima-yorozu.xml) が公開されたら、HTTP 200、XML、件数、代表の公式リンク、配信内容を反映コミットと照合する。定期更新で実際に新着が入ったときも、最初の反映と同様にPagesまで更新されたことを確認する。反映に遅延がある場合はPagesのデプロイ履歴を確認し、サイト全体の公開設定の変更は別途判断する。
6. 進行管理の承認範囲で、Inoreaderへ新規RSSとして登録し、代表記事の受信・リンクと旧購読との重複を確認する。旧購読は履歴を保持できる無効化を候補とし、新規RSSが新着を受信してから判断する。Excel等への反映は運用切替の確認後に行う。
